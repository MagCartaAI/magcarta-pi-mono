- [x] [MEDIUM] Broaden the envelope builder — “missing required field or a mistyped value” The validation boundary is unclear for correctly typed but contract-invalid values. The consumed schema requires positive integer row_limit, nonnegative integer range offsets, valid URLs, and nonempty connection references. It also requires key to exist for list, although this spec says key is required “UNLESS operation === list.” Implementers can emit different invalid envelopes while satisfying the stated type checks. -> State whether new extractors enforce all referenced request-schema constraints or only an explicit subset. Clarify that list permits an empty string key, and specify whether an omitted key is rejected or normalized.
  - CLOSED 2026-11-15: extractors enforce the full referenced constraint set (positive `row_limit`, `range` nonnegative + `start<=end`, valid `browser` URL, nonempty `connection_ref`). `FileReadConnectorRequest` clarified: `key` omitted = empty string, so `get`/`head` throw and `list` maps to a bucket-root listing; `list` accepts an empty string key.
- [x] [MEDIUM] Envelope-driven executor methods — error normalization and successful response parsing “Error normalization SHALL match the LLM path” conflicts with the unqualified instruction to return response.json() on success. The LLM path converts JSON parse failures to GatewayUnavailable (src/providers/gateway-llm.ts:203–208); direct passthrough exposes the raw parse error. The malformed-success response behavior is unresolved. -> Specify the error class for an unreadable successful response body, while preserving unchanged passthrough for successfully parsed JSON. Add that failure case to acceptance intent.
  - CLOSED 2026-11-15: a 200 with a body whose `response.json()` rejects throws `GatewayUnavailable` (mirrors `gateway-llm.ts:203-208`); successfully parsed JSON passes through unchanged. Added executor-test row "200 non-JSON body → GatewayUnavailable" and a malformed-success scenario.
- [x] [MEDIUM] Per-tool connector-mode branching — proxy dispatch and preserved lifecycle Local execution receives AbortSignal, but the pinned envelope-taking executor signatures do not. The spec does not define cancellation behavior before or during proxy dispatch. A cancelled loop can therefore continue issuing remote mutations or wait indefinitely for an in-flight request, depending on implementation choices. -> Define cancellation semantics within the pinned interface: whether cancellation prevents subsequent dispatches, how an in-flight result is handled, and which cancellation guarantees are unavailable. Add acceptance intent for cancellation between tool calls.
  - CLOSED 2026-11-15: defined in "Abort / cancellation" — the pinned signatures take no `AbortSignal`, so an in-flight fetch completes its round-trip; no between-call `signal.aborted` check exists today and none is added (deferred to the phase that can change the interface, recorded as a known limitation). Scenario states the in-flight call produces its result and the next queued call is skipped only via the existing steering mechanism.

  - CLOSED 2026-11-15: removed the false "existing between-iteration abort check" claim. - [x] [MEDIUM] Gateway result → AgentToolResult adapter, lines 530–533 and 571–576 The adapter must return an isError AgentToolResult, but AgentToolResult has no isError field (packages/agent/src/types.ts:162–167). The preserved loop sets its separate isError flag only when execution throws (agent-loop.ts:391–430). Returning a validation-error result therefore leaves the emitted event and ToolResultMessage marked successful. -> Specify that adapter validation failures throw an error naming the action and validation failure. The existing loop catch then produces the error result and sets isError on both outputs.
  - CLOSED 2026-11-15: adapter now throws on parse/validation failure naming the action id; the preserved `executeToolCalls` catch produces the `isError` tool result and marks event + `ToolResultMessage` `isError:true`. A malformed result is a contract violation, not a tool error.
- [x] [MEDIUM] Gateway result → AgentToolResult adapter, lines 525–530 Validation selects the schema using binding.connector_type, but file read, write, and delete all use type "file" and have distinct result schemas. The spec does not require validation against the dispatched action. An implementer could accept a valid FileDeleteResult returned from executeFileWrite instead of reporting the mismatched response. -> Require schema selection by connector_type and the dispatched action_id. State that a result valid only for another file action is a malformed result.
  - CLOSED 2026-11-15: schema selection now keys on `binding.connector_type` AND the dispatched `action_id`; a result valid only for another file action is a malformed result.
